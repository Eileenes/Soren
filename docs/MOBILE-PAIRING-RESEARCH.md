# 下载手机 App、扫码关联 Mac：可行性与实施方案

2026-10-12。结论：可以采用这一体验。本文件记录设计依据；0.4 已实现配对协议、中继、移动任务入口和 iOS 工程，实际交付边界以 [MOBILE-040-DELIVERY.md](MOBILE-040-DELIVERY.md) 为准。公共服务尚未部署。

## 参考项目核查

核查 [Happy GitHub 仓库](https://github.com/slopus/happy) 的 README、移动端说明和以下源码；未部署或授权第三方服务，未复制其代码：

- [手机端说明](https://happy.engineering/mobile-app/)：提供手机 App 和扫码关联，并通过中继连接电脑。
- [authQRStart.ts](https://github.com/slopus/happy/blob/main/packages/happy-app/sources/auth/authQRStart.ts)：客户端生成密钥对，把公钥登记为认证请求。
- [authQRWait.ts](https://github.com/slopus/happy/blob/main/packages/happy-app/sources/auth/authQRWait.ts)：等待服务端批准状态，并在客户端解密返回内容。
- [authApprove.ts](https://github.com/slopus/happy/blob/main/packages/happy-app/sources/auth/authApprove.ts)：已有身份的客户端确认待处理请求，以认证令牌提交批准。

这些代码表明，“扫码即可用”的背后包含设备密钥、已有身份授权和在线认证接口。二维码本身不负责长期传输。Happy 有自身会话协议，不能将其 App 直接连接到当前 Soren API。

## Soren 的使用流程

1. Mac 初始化本地空间和主设备身份，配置模型。本地使用及未来设备配对均不以 GitHub 登录为前提。
2. 用户下载 Soren iOS/Android App，点击「扫描 Mac 二维码」。
3. Mac 的「关联手机」显示一次性二维码；手机扫描后，Mac 显示新设备名称及双方一致的配对确认码。
4. 用户在 Mac 核对并批准。手机获得属于同一空间的独立设备凭据，不复制 Mac 的模型 API Key。
5. 手机显示同一组 Bot、任务和成果，可以发起任务和批准操作。Mac 继续执行，手机显示真实进度。
6. Mac 的设备列表可撤销某台手机；被撤销的设备立即失去访问能力。

2026-10-12 后续调整：以同一本地空间和可信设备身份为基础，不强制 GitHub 账号。手机经 Mac 确认配对，已有其他空间时明确切换、禁止自动合并。只有将来提供可选云账号服务时才考虑 GitHub OAuth；其部署不影响本地使用。

## 技术路线

优先对 **Tauri 2 移动壳 + 现有 React 界面**做真机验证，以复用页面和业务类型。[Tauri 官方文档](https://v2.tauri.app/develop/)提供 iOS/Android 开发入口，[官方扫码插件](https://v2.tauri.app/plugin/barcode-scanner/)提供相机扫码能力。这里只确认平台能力，不代表当前桌面项目可直接打出手机包。

需要将桌面 Go sidecar、菜单栏、Keychain、文件导出等入口与手机运行时分开。手机不启动 Go 服务，不使用 `127.0.0.1:8080` 当作 Mac 地址；网络层抽象为已认证的设备连接，直接接入产品方的加密中继。相机权限、深链接、凭据安全存储、推送和前后台恢复需分别验证。若真机验证无法达到交互要求，再评估独立 React Native 客户端，不先重写全部界面。

服务由产品方部署并内置地址。最终普通用户只下载 App、配对和配置模型，不需要自己购买服务器或创建 GitHub OAuth App。当前项目没有托管服务与正式应用凭据，需要由产品开发阶段补齐。

| 接入方式 | 使用范围 | 所需工作 |
| --- | --- | --- |
| 在线中继（正式版推荐） | 手机蜂窝网络或异地 Wi-Fi | HTTPS/WSS 服务、设备身份会话、设备注册及认证、续传、部署 |
| 局域网直连（未实现的可选路线） | 同一可互通网络，离开后不可用 | 独立配对监听端口、设备鉴权、可信加密通道、局域网权限和发现；不能直接开放当前本地 API |

没有服务器也可以开发并在本地验证协议；当前采用本地中继验证完整协议，正式异地连接使用产品方部署的同一中继。异地稳定可用不能仅靠二维码实现。

## 配对和消息约束

- 配对挑战一次有效，5 分钟过期，绑定空间、Mac 身份、临时公钥及协议版本。二维码不包含模型 Key、GitHub Token 或可长期复用的访问密钥。
- Mac 的批准绑定新手机公钥与双方核对的确认码，防止中间服务替换设备身份。使用成熟的加密协议和库，端到端加密需独立验证，未完成前不作此承诺。
- 每台手机独立凭据，存入系统安全存储；接入网关或中继校验配对建立的空间归属、设备状态与权限。扫码成功不代表后续消息可跳过认证。
- Mac 主动建立中继连接，家庭路由器通常不需要手动开放端口。中继不能伪造任务成功；收到 Mac 回执后才更新执行状态。
- 请求包含唯一 ID、事件序号和有效期；断线重连只续传，不能重复执行发邮件等副作用。手机确认也必须绑定具体参数版本。
- Mac 退出、休眠或断网时显示离线；云端中继不代替 Mac 执行 Bot。手机后台依赖系统通知和恢复，不假设长连接一直存活。

## 交付顺序和验收

1. **中继闭环**：在隔离环境完成本地空间/设备身份、Mac 主动连接、配对/撤销和请求去重；再接入真实业务 API。开发机运行中继不需要云账号。
2. **手机真机**：移动 App 完成扫码、Bot 列表、任务详情、审批与成果，复用已有响应式页面；手机与 Mac 操作同一份数据。完成平台签名和测试分发配置。
3. **异常验收**：验证过期二维码、其他空间设备、替换公钥、撤销设备、网络地址变化、断网、重启和重复请求，不得越权或重复发送。局域网受网络隔离限制，不能承诺任意同名 Wi-Fi 都可互通。
4. **远程版本**：部署域名、中继和设备身份服务，Mac 主动建立连接；验证设备间内容加密、异地网络、前后台恢复及通知，再交付远程使用入口。该部署由产品方承担。

第一阶段验收目标：手机安装测试版 → 扫 Mac 二维码 → Mac 确认 → 手机选择已有 Bot 并提交任务 → Mac 执行 → 两端看到一致结果。无需复制模型 Key 或再次创建 Bot。
